# Portable fleet label vocabulary (SSOT)

Repo Template owns the **portable** fleet label vocabulary that every adopted repository
bootstraps with. Fleet Registry responsibility map question
`portable-repo-template-and-label-vocabulary` points here.

## What this repo owns

| Layer | Authority | Location |
| --- | --- | --- |
| Code fleet-law projection (priority / work-spine / intake / banned) | Code publishes; Template consumes | `scripts/generated/fleet-law-projection.v1.json` via `scripts/generated/fleet-law.ts` |
| Template-portable additions (`agent-review`, `needs-rebase`, …) | Repo Template | `TEMPLATE_PORTABLE_LABELS` in `scripts/provision-canonical-labels.ts` |
| Composition + provision plan | Repo Template | `buildCanonicalLabels()` / `pnpm provision:labels` |
| Sync/check against Code source | Repo Template | `pnpm check:fleet-law` / `pnpm verify:fleet-law` |
| Charter claim | Repo Template | `AGENTS.md` TEMPLATE-SELF **Responsibilities** (label vocabulary bullet) |

## What this repo does not own

- Authoring or revising Code fleet-law projection bytes (Code `tools/work-spine`).
- Consumer-only or product-specific labels outside the portable kit.
- Live GitHub label mutation for already-adopted repos merely because the template kit changes
  (adoption/refresh paths stay effect owners).

## Operator commands

```bash
pnpm check:fleet-law          # generated consumer matches the selected Code source
pnpm verify:fleet-law         # self-test + check
pnpm provision:labels --dry-run
node scripts/provision-canonical-labels.selfcheck.ts
```

## Published taxonomy consumption (repo-template#468 / code#7581)

The bundled revision-2 fleet-law projection is generated by Code and copied only by
`scripts/check-fleet-law-sync.ts --sync`. Set `CODE_REPO_ROOT` to the selected Code source
when syncing from an isolated checkout. Template verifies the projection schema, content
digest, assessment identity and label semantics; it does not author the JSON or require the
retired `governedIntakeProducer` pin. A legacy pin, if present, must remain internally
consistent, but it never admits a live provision operation.

Code #8389 supplies the published revision-23 projection. The Code source/digest provenance
and the Governed Intake producer commit/payload digest describe distinct artifacts and are
recorded separately. Their values are evidence of the consumed bytes, not requirements that
future publications equal the same commit or revision. Historical #476/#477 preparation and
#479's partial live resolver remain conserved in their commits and issue receipts.

Dry-run composition supports multiple `delivers`, `type`, and `source` values; exactly one
current `progress`; independent blockers; and structured risk, authority, and environment.
`type:regression` needs prior behavior/decision evidence. Benefits are intended outcomes,
not measurements. Priority is independently assessed from evidence; label edits/counts never
change it. `metadata:triage-vN` is the sole completion family. Provisioning that label's
repository definition does not stamp an issue or establish semantic completion.

At every provision operation, `scripts/governed-intake-release.ts` resolves the current
`spencer-shadley/.github` default branch and its HEAD commit in one symbolic-ref observation, reads its immutable release manifest, and retrieves
every declared payload from that same commit. It checks byte lengths and SHA-256 values
before executing that publication's integrity-bound `verify.js` over the materialized
release. The producer owns required files, alias equality, schema, owner and contract-policy
consistency. Template carries no production copy of that required-file list or verifier.
A later producer can strengthen its verifier without a Template source change; unsupported,
unreadable or rejected releases fail closed.

The verifier child inherits no credentials, has bounded execution, and receives filesystem
read permission only for the temporary release directory. Node permissions are defense in
depth for trusted producer code, not a network sandbox. The directory is removed on success
and failure. Only a successful actual producer verification creates a process-local verified
release object; a structurally identical caller-made object cannot authorize provisioning.

Dry-run uses the same resolver and records the actual publication head, producer commit,
revision and payload digest. There is no serialized-ready, tier, old namespace or static
revision fallback that authorizes writes. Live adoption remains the authorized consumer's
own transaction; changing this kit does not provision every existing repository.

Non-delivery closure retains last actual progress. `resolution:obsolete` closes genuinely
valueless accepted work after its direction decision, with the exact causing issue and
accepted decision comment and a backlink on the cause. `resolution:superseded` conserves
still-valid work at its destination. Reopening clears resolution and invalid stamps and
requires current published assessment. Provisioning preserves unrelated labels and does
not delete retired repository labels from closed history by default. Stock migration stays
with the programme owner. GitHub native inheritance remains the only form distribution:
no `.github/ISSUE_TEMPLATE/**` copies.

The owning selfcheck includes valid full-release, missing required payload, corrupt
noncanonical payload, alias mismatch and future-verifier requirement controls. Projection
fixtures cover the current pinless shape and corrupt assessment identity. These checks
establish source behavior; actual release/adoption readback remains separately recorded.

This migration follows P0.1 (producer ownership/custody), P1.2 (fail-closed release evidence),
and P2.1 (bounded reversible preparation). The adopt-project label provisioning step uses
the same authorized current-release flow; no form-copy instructions are added.
